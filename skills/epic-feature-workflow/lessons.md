# Cross-epic decomposition lessons

> Read by `pi-epic-decompose` BEFORE proposing a new decomposition.
> Updated by `pi-epic-complete` distilling generalizable patterns from each
> epic's `deviations.md`. Append-only; supersede entries by adding a new one
> with `Supersedes: <id>`.

## Format

Each lesson:

```
### L-NNN: <one-line title>
- **Added:** YYYY-MM-DD (epic <epic-id>)
- **Pattern:** <when this applies>
- **Lesson:** <what to do / not do at decomposition time>
```

## Lessons

### L-019: `pi-feature-start` must auto-commit the scaffolded feature folder
- **Added:** 2026-05-14 (epic 0001-partner-agent-sdk-hardening, all 42 done features)
- **Pattern:** `pi-feature-start` writes `feature.md` and `meta.yaml` into the main repo's epic-branch worktree as **untracked** files. The worker (in its own feature worktree) later writes a populated `feature.md`. When `pi-feature-complete` squash-merges the feature branch, git refuses: `error: The following untracked working tree files would be overwritten by merge: .pi/epics/.../features/<fid>-<slug>/feature.md, meta.yaml`. Even worse on the second pass: pre-committing the *template* version creates a divergent add/add conflict against the worker's *populated* version on squash-merge (CONFLICT add/add in `feature.md`). Partner-agent-sdk hit this on every feature; user did manual git surgery 42 times.
- **Lesson:** `pi-feature-start` commits the freshly-scaffolded feature folder + `STATE.md` to the epic branch immediately after creating them, as a `chore(epic): scaffold <fid> feature folder` commit. Then both branches share the same parent commit for those paths, and squash-merge's existing journal-auto-resolve path (taking `--ours`, the main-repo version) handles the natural divergence cleanly. Implemented in `pi-feature-start` 2026-05-14.

### L-020: `pi-epic-validate-decomposition` must reject unsafe-leading-char AC strings
- **Added:** 2026-05-14 (epic 0001-partner-agent-sdk-hardening)
- **Pattern:** Partner-agent-sdk's `decomposition.yaml` had AC strings like `- *.invariants.yaml schema validated on load.` — the unquoted leading `*` makes strict YAML parsers (PyYAML, `yaml.safe_load`) interpret it as an alias reference and fail outright. The orchestrator and scripts use a lenient hand-rolled parser that tolerates this, so the file "worked" the entire epic. But it's a latent footgun: any future tooling that uses a real YAML library breaks. Eighteen AC entries had this shape.
- **Lesson:** `pi-epic-validate-decomposition` errors on any unquoted AC entry whose first character is `*`, `&`, `!`, `|`, `>`, `%`, `@`, or backtick. Tells the user to quote it. Same rule belongs in `/epic-decompose` step 1 — propose quoted versions when these chars appear. Implemented 2026-05-14.

### L-021: `scope_files` non-glob paths whose parent dir is missing are likely stale
- **Added:** 2026-05-14 (epic 0001-partner-agent-sdk-hardening, F24)
- **Pattern:** Partner-agent-sdk F24 listed `PartnerAgentSDK/PX.Partner.Agent.sln` in `scope_files`. The repo has no `PartnerAgentSDK/` directory; the actual file is `PX.Partner.Agent.sln` at the repo root. Stale carryover from an earlier layout proposal. Worker edited the right file and logged a deviation, but the noise compounds over 53 features.
- **Lesson:** `pi-epic-validate-decomposition` walks every non-glob `scope_files` entry. If the file doesn't exist AND its parent dir doesn't exist, emit a warning (likely stale). If the parent exists but the file doesn't, skip silently (feature may create it). Same check applied to epic-level `reference_paths`. Implemented 2026-05-14.

### L-022: known-flake handling — deferred to v0.5.1+
- **Added:** 2026-05-14 (epic 0001-partner-agent-sdk-hardening, F19 + F21-F42 chain)
- **Pattern:** F19 left a timing-sensitive test (`ThreeHundredMsLoad_RunsConcurrently_InUnder250Ms`) that passes in isolation but fails under solution-wide parallel test load. Every subsequent M3 feature paid the `--skip-tests` tax to merge, with a deviation entry each time. ~22 features paid that tax.
- **Lesson:** Add a first-class `known_flakes:` array to `epic-config.yaml` that `pi-feature-complete` honors: each entry has `test_filter` (string passed to the test runner to exclude) + `reason` + `expires` (date). On every feature merge, log one deviation entry naming the flakes that were excluded. Deferred to v0.5.1 to keep v0.5.0 scope bounded; the current `--skip-tests` workaround still works.

### L-016: `python` vs `python3` — propose the interpreter that exists
- **Added:** 2026-05-14 (epic 0001-taskq, sample run)
- **Pattern:** Modern Debian / Fedora / Arch / many container images ship `python3` only — there's no `python` symlink. `/epic-decompose` Step 3 was hardcoded to propose `python -m pytest -q` whenever a `pyproject.toml` was found. `pi-feature-complete` runs `bash -c "$test_cmd"` literally, so the missing shim makes every feature halt at H1 even when the worker's tests pass cleanly under `python3`. The F01 worker on epic `0001-taskq` had to patch `epic-config.yaml` itself, log a deviation, and continue.
- **Lesson:** `/epic-decompose` Step 3 must check `command -v python3 || command -v python` (in that order) and propose the interpreter that actually exists. The same logic belongs in any future `pi-epic-init`-side autodetect. (Prompt updated in `prompts/epic-decompose.md` 2026-05-14.)

### L-017: `.gitignore` must exclude `halt-*.md` (belt for L-012's suspenders)
- **Added:** 2026-05-14 (epic 0001-taskq, sample run)
- **Pattern:** L-012 fixed the most common halt-file leak path (`pi-feature-start`'s auto-commit train) with a targeted `git reset HEAD halt-*.md`. But the orchestrator's BLOCK-recovery step in FINALIZE re-stages `.pi/epics/<id>/` after the epic-reviewer flags issues, and the prompt was ambiguous enough that the orchestrator interpreted "stale halt report" as "file to archive into the commit" rather than "file to delete." Result on the taskq run: `halt-2026-05-14T0400Z.md` rode the `chore(epic): epic review + archived halt report` commit straight onto `epic/taskq` and would have been in the PR diff.
- **Lesson:** Defense in depth. (a) `pi-epic-init` adds `.pi/epics/*/halt-*.md` and `.pi/epics/done/*/halt-*.md` to `.gitignore` so even a stray `git add` typo can't stage one. (b) The orchestrator's FINALIZE step explicitly says "stale halt = `git rm` + `rm`, never `git add`" with a worked example. (c) The closeout-retry block carries the same `git reset HEAD halt-*.md` belt as the main closeout. (Implemented in `pi-epic-init` + `prompts/epic-run-auto.md` 2026-05-14.)

### L-001: pre-populate `.gitignore` with pi runtime artifacts at epic-init
- **Added:** 2026-05-12 (epic 0001-task-cli)
- **Pattern:** Repos using `pi install -l` for `pi-subagents` / `pi-intercom` create `.pi/npm/` and `.pi/settings.json`. The orchestrator's per-feature `worker-report.md`, `review-report.md`, `progress.md` are also runtime state, not source.
- **Lesson:** `pi-epic-init` must add `.pi/npm/`, `.pi/settings.json`, and the per-feature ephemeral report patterns to `.gitignore` as part of its scaffolding commit. Otherwise these untracked files dirty the tree and either block `pi-feature-start`'s clean-tree check or get accidentally committed. (Implemented in `pi-epic-init` 2026-05-12.)

### L-002: never use `|` as a sed delimiter on YAML scalar values
- **Added:** 2026-05-12 (epic 0001-task-cli)
- **Pattern:** Feature titles, summaries, and design text legitimately contain shell metacharacters (`|`, `/`, `&`, `\`). Any script that splices them into a `sed s|...|...|` command will crash on a perfectly valid title.
- **Lesson:** For in-place edits on `meta.yaml` / `feature.md` from values that originate in user-authored YAML, prefer a tiny embedded `python3 -` block over `sed -i`. Sed delimiters are landmines for content the user authored.

### L-003: skill scripts must fail loudly when run from the wrong cwd
- **Added:** 2026-05-12 (epic 0001-task-cli)
- **Pattern:** `pi-feature-complete` and similar scripts assume the main repo cwd (where `.pi/STATE.md` lives). Run from a feature worktree, they would silently no-op (exit non-zero with no stderr) because `active_epic_id` returned 1 with no message.
- **Lesson:** Helpers in `_common.sh` that resolve epic state must print a *specific* error to stderr explaining the likely cause ("are you in a worktree? cd to main repo") rather than `return 1` silently. Also: orchestrator templates must explicitly `cd` to the main repo before invoking these scripts — don't assume cwd. (Implemented in `_common.sh::active_epic_id` 2026-05-12.)

### L-004: `pi-feature-complete` must be defensive about post-merge journal state
- **Added:** 2026-05-12 (epic 0001-task-cli)
- **Pattern:** Squash-merging from a feature branch can interact badly with journal files (`feature.md`, `meta.yaml`) edited only on the epic branch by the orchestrator. After `mv $feat_dir done/`, the script's `sed -i` on `$moved_dir/meta.yaml` can fail if the file is missing for any reason — and `set -euo pipefail` propagates the failure up, leaving the merge committed but the archive incomplete.
- **Lesson:** Any post-merge file munging in `pi-feature-complete` should be wrapped in existence checks with a fallback that *reconstructs* a minimal `meta.yaml` (id, state=merged, branch, merge_sha, dates) rather than aborting. The merge has already happened; failing to update meta.yaml is a recoverable cosmetic issue, not a reason to leave the epic in an inconsistent state. (Implemented in `pi-feature-complete` 2026-05-12.)

### L-005: orchestrator must do its budget check at the TOP of the loop
- **Added:** 2026-05-12 (epic 0001-task-cli)
- **Pattern:** With a `--max-features=N` cap, naive orchestrators check the budget AFTER `pi-feature-complete` of the in-flight feature, but BEFORE that they've already called `pi-feature-start` for the NEXT feature — leaving an orphan worktree, branch, and `meta.yaml: state: in-progress` when the cap fires.
- **Lesson:** The budget check is step 0 of the loop, before `pi-epic-next-feature`. Same applies to wall-clock and token budgets. Never call `pi-feature-start` if the next iteration won't be allowed to complete.

### L-006: orchestrator must NOT make cleanup commits on the user's behalf
- **Added:** 2026-05-12 (epic 0001-task-cli)
- **Pattern:** When the working tree is dirty (real source/test changes, not orchestrator artifacts), it's tempting for the orchestrator to `git add -A && git commit -m "chore(epic): pending edits"` to unblock `pi-feature-start`. This silently absorbs user work into a chore commit on the epic branch, polluting the eventual PR.
- **Lesson:** `pi-feature-start` already auto-commits anything under `.pi/epics/<id>/` and `.pi/STATE.md` to the epic branch (intentional, scoped). For dirty paths OUTSIDE that scope, the orchestrator must HALT (H2) and let the human commit / stash / revert. Never `git add .` or `git commit -a` on the epic branch from the orchestrator.

### L-007: per-feature artifact paths are ephemeral after `pi-feature-complete`
- **Added:** 2026-05-12 (epic 0001-task-cli)
- **Pattern:** Orchestrators that spawn a follow-up subagent (e.g. "verify the merge") with `output: <FEATURE_DIR>/something.md` AFTER `pi-feature-complete` will write to the (now non-existent) original path — `subagent` recreates the parent directory, leaving stale artifacts in `features/<F>/` while the canonical archive is in `features/done/<F>/`.
- **Lesson:** Treat `FEATURE_DIR` as ephemeral after `pi-feature-complete`. If post-merge subagents are needed, point them at `EPIC_DIR/features/done/<F-slug>/` explicitly. The orchestrator template's step 12 makes this explicit.

### L-008: pass absolute paths to feature-worker / feature-reviewer subagents
- **Added:** 2026-05-12 (epic 0001-task-cli)
- **Pattern:** Workers/reviewers run with `cwd` = the feature worktree. The feature folder (`feature.md`, `meta.yaml`, `decomposition.yaml`) lives only in the *main repo's* `.pi/epics/<id>/`, not in the worktree (because `pi-feature-start` writes them after branching). A worker reading `".pi/epics/<id>/features/<F>/feature.md"` from cwd finds nothing.
- **Lesson:** When delegating to a per-feature subagent, the orchestrator must pass `MAIN_REPO=`, `EPIC_DIR=`, `FEATURE_DIR=`, `FEATURE_ID=` as absolute paths in the task message. The worker/reviewer reads from those absolute paths; only code/tests are written inside the worktree.

### L-027: decomposition.yaml `acceptance_criteria` is normative; `summary` is informative
- **Added:** 2026-05-14 (epic 0001-smoke, epic-reviewer note)
- **Pattern:** Smoke epic F03's `summary` said compaction preserved insertion order "via position of latest surviving SET". F03 AC 6 + design §4 required first-occurrence order. Applied to the AC script literally, the summary's rule yields `[c, b]`; the AC + design require `[b, c]`. Worker correctly followed the AC; epic-reviewer caught the drift post-hoc and called out the internal contradiction in decomposition.yaml. No functional impact, but it's a foot-gun the next decomposer would re-walk into.
- **Lesson:** `decomposition.yaml` template now carries a header comment: `acceptance_criteria` is normative — what `pi-feature-complete` and the reviewer measure against. `summary` is informative — prose context for humans and the planner. On conflict, implementation MUST follow AC. Decomposers re-read each summary against its AC list before finalizing and rewrite the summary as a one-line restatement of the AC + design references if they disagree. (Implemented in `templates/decomposition.yaml` 2026-05-14.)

### L-026: `.gitignore` template must cover `.pi/epics/done/<id>/` paths too
- **Added:** 2026-05-14 (epic 0001-smoke, post-completion observation)
- **Pattern:** Original gitignore patterns were `.pi/epics/*/features/*/worker-report.md` and similar — each `*` matches exactly ONE path segment. After `pi-epic-complete` moves the epic to `.pi/epics/done/<id>/...`, the path gains an extra segment (`done/`) and the patterns stop matching. `git add -A` after archive happily tracks worker/review/progress reports and the run-log. The smoke epic shipped its reports into the archive commit before this was caught. Separately: bytecode caches (`__pycache__/`, `*.pyc`) were absent from the template, so a Python project (smoke epic kvstore) had 11 `.pyc` files baked into the epic branch.
- **Lesson:** `pi-epic-init` now also adds `.pi/epics/done/*/run-log.jsonl`, `.pi/epics/done/*/features/done/*/worker-report.md` (and `review-report.md`, `progress.md`), plus universally `__pycache__/` and `*.pyc`. Universal bytecode ignores are cheap noise on non-Python repos and real hygiene on Python ones; the conditional gating wasn't worth the complexity. (Implemented in `pi-epic-init` 2026-05-14.)

### L-025: `pi-epic-complete` must commit the epic-archive rename, not just `mv`
- **Added:** 2026-05-14 (epic 0001-smoke, post-completion observation)
- **Pattern:** `pi-epic-complete` was doing a plain `mv .pi/epics/<id> .pi/epics/done/<id>` on the filesystem after the closeout + epic-review commits, but didn't `git mv` and didn't commit the rename. Result: epic ended with `git status` reporting `D` for the old paths + `??` for the new ones. Working tree dirty after the documented "final step" of the workflow. Required manual `git add -A && git commit` to recover. Same flavor of bug existed in `pi-feature-complete` (the `mv features/<fid> features/done/<fid>` was being silently swept up by the next `pi-feature-start`'s pending-edits commit, which worked for sequential features but left the last feature in an epic in dirty state).
- **Lesson:** Both scripts now: prefer `git mv` (stages the rename in one operation), fall back to `mv` + `git add -A` if git refuses (untracked files in the source). `pi-epic-complete` additionally sweeps the destination for newly-written siblings (`lessons-candidate.md`, future epic-review artifacts) that the rename didn't pick up. Commit messages: `chore(epic): archive <id> to .pi/epics/done/` and `chore(epic): archive <fid> to features/done/`. Smoke-test step 8 enforces a clean tree post-`pi-epic-complete`. (Implemented in `pi-epic-complete` + `pi-feature-complete` 2026-05-14.)

### L-024: decomposer must include symbol-owning files in `scope_files`
- **Added:** 2026-05-14 (epic 0001-smoke, F03 deviation)
- **Pattern:** Smoke epic F03 AC 4 literally said `kvstore.errors.LockedError` must raise on lock contention. F03 `scope_files` was `[engine.py, test_engine.py]` — `errors.py` was NOT in scope, despite the AC naming a symbol that lives there. Worker was forced into an out-of-scope edit (added `LockedError` class + re-exported from `__init__.py`) and the reviewer logged it as a deviation. Same pattern would burn every cross-cutting AC: `model.errors.X`, `package.module.Class`, etc.
- **Lesson:** When an AC names a fully-qualified symbol path, the decomposer must add the file owning that symbol to this feature's `scope_files` — OR ensure the symbol already exists on the epic branch via a merged dependency. `prompts/epic-decompose.md` Step 1 has the L-024 callout. `pi-epic-validate-decomposition` emits a warning when an AC contains `dotted.module.ClassName` and no `scope_files` entry (own or dep's) heuristically maps to `dotted.module`. Heuristic resolution: strip leading `src/`, `lib/`, `app/`, `source/`; treat `pkg/module.py` and `pkg/module/__init__.py` as owners of `pkg.module`. Warn-only — false positives don't block. (Implemented in `prompts/epic-decompose.md` + `pi-epic-validate-decomposition` 2026-05-14.)

### L-023: `pi-feature-complete` spike path needs three structural fixes
- **Added:** 2026-05-14 (epic 0001-smoke, S01 deviation)
- **Pattern:** Spikes (`kind: spike`, deliverable is a decision in `deviations.md`, not code) revealed three interlocking bugs in v0.5.0 the first time one ran end-to-end:
  1. **Empty squash.** `pi-feature-start` committed the scaffold to the epic branch AFTER creating the feat branch; feat branch pointed at the pre-scaffold tip. For spikes (no code in worktree), the feat branch had zero commits relative to epic when `pi-feature-complete` ran. `git merge --squash` produced an empty diff; the script bailed.
  2. **Checkout-blocking journal in MAIN_REPO.** The spike worker writes journal artifacts (populated `feature.md`, appended `deviations.md`) directly to MAIN_REPO's epic-branch working tree. Those edits were uncommitted at `pi-feature-complete` time, so the subsequent `git checkout epic/<slug>` failed with "local changes would be overwritten by checkout".
  3. **L-004 `--ours` resolver wiped the journal on retry.** When the human worked around (1)+(2) by manually cherry-picking journal commits onto feat and re-running, the L-004 auto-resolver kicked in on the resulting add/add conflict and took the EPIC-branch version — which was the empty scaffold. Populated journal contents were silently discarded. Recovery required `git reflog` + a manual `fix(<spike>): restore journal` commit.
- **Lesson:** Three structural fixes:
  1. `pi-feature-start` now commits the scaffold to the epic branch BEFORE creating the feat branch. Feat inherits the scaffold; non-spike features behave identically (same files they'd write on top of anyway).
  2. `pi-feature-complete` for `kind: spike` commits any uncommitted journal edits in MAIN_REPO to the epic branch FIRST as `spike(<id>): decision + journal`. This is the spike's actual deliverable. `git checkout epic/<slug>` then succeeds; the subsequent `git merge --squash $feat_branch` is empty (feat has only scaffold) and is allowed via `--allow-empty` for spikes only.
  3. L-004 resolver path is now unreachable for spikes (the feat branch carries no journal diff to conflict with). The `--ours` rule remains correct for non-spike features.
- (Implemented in `pi-feature-start` + `pi-feature-complete` 2026-05-14; smoke-test step 7 enforces the spike path end-to-end.)

### L-031: spike id position should reflect the spike's DAG position, not always `S01`
- **Added:** 2026-05-14 (gen-ui epic decomposition, post-v0.5.1)
- **Pattern:** The smoke epic numbered its spike `S01` and put it first in dependency order (`S01, F02, F03, F04`). The gen-ui epic numbered its spike `S04` and placed it after `F01..F03` because the spike actually depends on catalog groundwork being done first. Both are valid mechanically (the dispatcher resolves spikes by their `depends_on` like any feature), but the gen-ui choice is clearer for readers: the id reflects DAG position, not just sequence in the spikes-section. Forcing all spikes to `S01..S0N` at the top of the file hides which features they actually gate.
- **Lesson:** Spike numbering rule: pick the id at the position in the dependency order where the spike's earliest blocked feature would naturally fall. If a spike blocks F04+, name it `S04` (placed after `F01..F03`). If a spike has no deps and gates everything downstream, `S01` is right. The numeric counter is still shared with features (you can't have `S03` AND `F03`). Encoded in `prompts/epic-decompose.md` Step 1 as the L-031 callout. (Implemented in `prompts/epic-decompose.md` 2026-05-14.)

### L-032: worker completion claims must be backed by evidence the reviewer can audit
- **Added:** 2026-05-14 (obra/superpowers review, pre-v0.6)
- **Pattern:** Pre-v0.6, the worker's report listed acceptance criteria as met but didn't show *how* they were verified. The reviewer's options were (a) re-run everything blind, (b) trust the worker, or (c) request a verbose progress dump. (a) doubles compute; (b) is exactly the hallucinated-success failure mode `feature-reviewer` was introduced to prevent in the first place; (c) is what most reviewers actually did, which is fine when it works but rubber-stamps when it doesn't. The reviewer needs an *audit-able artifact* per AC, not the worker's word + a re-run.
- **Lesson:** The worker's `worker-report.md` MUST contain a `## Completion evidence` section with one `### AC<N>:` block per acceptance criterion, each containing the literal command run + the last ~20 lines of stdout/stderr (or, for code-shape ACs, a file:line citation + structural claim). `pi-feature-complete` enforces presence of the header at the shell layer (refuses to merge if missing for a non-spike feature). The reviewer is required to spot-check at least one block by re-running the command and comparing output (fabricated evidence → REQUEST_CHANGES). Spikes are exempt: their evidence lives in the spike template's §3 Options + §5 Decision + the `deviations.md` entry. The reviewer also gets a credibility-clause rider: either name one concrete weakness, or list three specific checks done — rubber-stamp APPROVE-with-no-findings is rejected. (Implemented 2026-05-14 in `agents/feature-worker.md`, `agents/feature-reviewer.md`, `pi-feature-complete --skip-evidence`.) **Borrowed concept from obra/superpowers `verification-before-completion`**, but landed as mechanical script-gate + reviewer must-cite, not as a prompt-only skill (see L-034).

### L-033: H10 — soft halt for ambiguous AC that shouldn't block the whole epic
- **Added:** 2026-05-14 (obra/superpowers review, pre-v0.6)
- **Pattern:** Pre-v0.6, halt codes H1–H7+H9 all stopped the entire epic and required the user to act before any other feature could continue. But many ambiguities (`AC: "prints TODO"`, scope_file pointing at a missing path, upstream deviation contradicting a downstream AC) are *localized* — they block this one feature, not the other ten dependency-independent features in the DAG. Forcing a full-epic halt for a single ambiguous AC stalls the run for minutes-to-hours just to fix one line.
- **Lesson:** Add halt code **H10** ("ambiguous AC, paused for human"). Triggers: literal `TODO`/`TBD`/`<placeholder>`/`???` in AC text, missing scope_file that isn't part of a 2+-file greenfield package (the L-030 case), upstream deviation that directly contradicts the AC, undefined `design.md` symbol the AC references, or 2+ materially-different valid readings of the AC. H10 is NOT for ambiguity-resolvable-by-reading-2-or-3-docs — go read first. On H10, the orchestrator marks the feature `state: halted-ambiguous`, writes a halt report with the planner/worker's exact question, and *continues to the next DAG-independent feature*. When the user resolves the AC (one-line edit to `decomposition.yaml` or `design.md`) and re-runs `/epic-run-auto`, `pi-epic-next-feature`'s in-progress-first rule (L-010) picks the halted feature back up. Recipe documented in `docs/recovery.md` R8. The halt family is now H1–H7, H9 (hard), H10 (soft). (Implemented 2026-05-14 in `agents/feature-planner.md`, `agents/feature-worker.md`, `prompts/epic-run-auto.md`, `docs/design.md`, `docs/recovery.md`.) **Inspired by obra/superpowers' "stop and ask" pattern**, but landed as a structured halt code the orchestrator parses, not as a prompt suggestion.

### L-034: every new rule needs a mechanical enforcement point
- **Added:** 2026-05-14 (obra/superpowers review meta-lesson, pre-v0.6)
- **Pattern:** Reviewing obra/superpowers (191k☆, broad influence in the agentic-tooling space) made the pattern obvious: most of its 14 skills are prompt-only rules ("the agent SHOULD verify before completing", "the agent SHOULD enumerate options before deciding"). They work when the model behaves well and fail silently when it doesn't, with no signal to the user. Pi-epicflow's lessons history (L-019 worktree-rename, L-023 spike-empty-squash, L-025 archive-rename-uncommitted, L-028 recovery-playbook, L-029 range-syntax, L-030 parent-dir false-positive) all share a structure: the original fix was a prompt suggestion; it kept failing; the durable fix was a shell-script gate or reviewer must-cite clause. The mechanical layer is pi-epicflow's actual leverage over a culture-pack-style skills bundle.
- **Lesson:** When adding a new lesson, halt code, or quality bar, it MUST land in at least one of: a `pi-*` script gate, a reviewer must-cite clause that maps to a REQUEST_CHANGES verdict, a structured field the orchestrator parses (halt codes, `state:` enums, `kind:`), or a template field the reviewer audits for completeness. Prompt-only rules are allowed only when there's no good mechanical proxy (e.g. anti-sycophancy clauses) and should be flagged as exceptions in the lesson entry. Documented as a top-level key design choice in `docs/design.md` ("Every rule has a mechanical enforcement point"). Apply on every future lesson. (Documented 2026-05-14 in `docs/design.md`.)

### L-030: validator's parent-dir-missing warning floods on greenfield packages
- **Added:** 2026-05-14 (gen-ui epic decomposition, post-v0.5.1)
- **Pattern:** `pi-epic-validate-decomposition` warns when a `scope_files` entry doesn't exist on disk AND its parent dir is also missing — the original intent was to catch stale paths from an earlier layout. On greenfield epics that build new packages (gen-ui has ~10 new directories, each with multiple planned files), this fires once per file: 50+ warning lines, all false positives. The decompose-prompt summary block has to roll them up into a single "All scope_files warnings are 'parent dir missing' — expected" note, which means real stale-path warnings would now be lost in the noise.
- **Lesson:** Pre-compute a per-directory file count across the entire decomposition. If 2+ scope_files share the same (currently-missing) parent dir, that's signal someone is intentionally building a new package — suppress the warning. If only 1 file is going into the missing dir, keep the warning (still likely stale). The warning message now also tells the user how to silence it explicitly: "add a second scope_file under '<parent>/' to confirm intent". (Implemented in `pi-epic-validate-decomposition` 2026-05-14.)

### L-029: `depends_on` range syntax silently breaks the DAG
- **Added:** 2026-05-14 (gen-ui epic decomposition, near-miss)
- **Pattern:** Decomposer writes `depends_on: [F06-F09]` (or `depends_on: F06-F09`) intending it as a range. YAML doesn't expand ranges — the dispatcher reads `"F06-F09"` as a literal single-string feature ID that doesn't match anything in the graph. Result: silent dependency violation (dispatcher treats this feature as having no deps when it should be gated on F06–F09). Pre-L-029 the validator emitted a generic `depends_on 'F06-F09' is not a defined feature` error, which is correct but doesn't point at the underlying mistake. The gen-ui decomposition almost shipped with five such entries (`F12, F13, F23, F26, F29, F30, F32` all had range strings in the summary view); user caught it during review.
- **Lesson:** (1) Decomposer prompt now has an explicit L-029 callout in Step 1 banning range syntax (`prompts/epic-decompose.md`). (2) `pi-epic-validate-decomposition` detects the range pattern with a regex (`^[FS]\d+-[FS]\d+$`) and emits a specific error with the fix inline: "Expand to an explicit list, e.g. depends_on: [F06, F07, F08, F09]". Hard error, not warning — silent DAG breakage is worth blocking commit. (Implemented in `prompts/epic-decompose.md` + `pi-epic-validate-decomposition` 2026-05-14.)

### L-028: orchestrator needs a written recovery playbook
- **Added:** 2026-05-14 (kvstore 0001-smoke S01 post-mortem, deferred from v0.5.1)
- **Pattern:** When the smoke epic's S01 spike hit the L-023 bugs, the orchestrator recovered by hand: `git reflog` to find the lost journal, `git checkout <sha> -- path` to restore, manual `fix(<spike>): restore journal` commit, then `pi-feature-complete --skip-tests` to resume. It worked only because the model went deep and was willing to read git plumbing docs mid-run. There was no written playbook to consult — the recovery sequence was reconstructed from first principles each time. Less persistent agents (or human users) would have given up and re-run from scratch, losing the worker's accumulated context. Same applies to other stuck states: empty squash, dirty tree post-mv, rebase-stale feat branches, half-finished `pi-feature-start`.
- **Lesson:** Write `docs/recovery.md` with seven named recipes (R1–R7) covering common stuck states: lost-journal restore, empty-squash recovery, dirty-tree post-`pi-feature-complete`/`pi-epic-complete`, feat-branch base drift, half-finished `pi-feature-start`, `--skip-tests` decision tree, and a final stop-and-halt rule at 15 minutes. Each recipe follows a fixed shape: Symptom → Root cause → Recovery commands → Verification → Prevention reference. Cross-linked from `prompts/epic-run-auto.md` §STALL HANDLING. Frequency dropped sharply under v0.5.1 (structural fixes to L-019, L-023, L-025 make most cases unreachable for new epics), but pre-v0.5.1 epics in flight + future bugs in the same family will still hit these. (Implemented in `docs/recovery.md` + `prompts/epic-run-auto.md` 2026-05-14.)

### L-035: defer the parallel-dispatch orchestrator; ship the manual-parallelism aid first
- **Added:** 2026-05-15 (v0.6.1 release planning, post-v0.6.0)
- **Pattern:** After v0.6.0 shipped, the obvious next big-feature candidate was a parallel-dispatch orchestrator: run multiple ready features concurrently in their worktrees, with a serial merge queue at the squash-merge step. Estimated ~16h to build correctly (orchestrator state machine + rebase-or-fallback protocol + halt isolation across N workers + smoke phases + recovery recipe). But: no real wall-clock evidence that serial dispatch is the bottleneck. The only data point (kvstore smoke epic, 4 features) is too small to matter; gen-ui hasn't run yet. Spending 16h on a 3×-cost feature based on speculation violates the project's no-bloat bias.
- **Lesson:** When a feature looks obvious but the user-pain evidence is missing, ship the smallest manual workaround first and write the full design as a sketch — don't build. For parallelism, this meant `pi-epic-status --ready` (≈50 lines of Python, near-zero risk, lets two pi sessions manually parallelize today) + `docs/sketch-parallel.md` (parks the full design for v0.7+). The sketch encodes a *decision gate*: ship the full orchestrator only when (a) one real ≥20-feature epic shows ≥30% serial-wait time in its run-log, or (b) two independent outside users ask for it, or (c) token-cost analysis says serial wall-clock cost > orchestrator build cost. Until then, manual parallelism is enough and we save the engineering hours for things with proven demand. Decisions like "no automatic rebase on out-of-order squash-merge — halt and ask" are also locked in the sketch so future-us doesn't have to re-derive the safety properties. Mechanical enforcement: this lesson lives next to the sketch; any PR that adds parallel-dispatch logic without referencing the decision gate gets reviewer pushback. (Implemented 2026-05-15 in `skills/epic-feature-workflow/scripts/pi-epic-status` and `docs/sketch-parallel.md`.)

### L-010: pi-epic-next-feature must prefer in-progress over ready
- **Added:** 2026-05-13 (epic 0001-minikv, halt-and-resume scenario)
- **Pattern:** When the orchestrator is interrupted mid-feature (halt, crash, user Ctrl+C, environment fix needed), the active feature's `meta.state` stays at `in-progress` and its worktree+branch persist. On resume, `pi-epic-next-feature` would scan for ready (pending + deps-met) features FIRST and only fall back to in-progress when none were ready. With multiple roots (e.g. F01 + F05 both depend_on=[]), this caused the script to silently skip the half-done F01 and start F05 instead, leaking F01's worktree and creating two parallel features for one orchestrator.
- **Lesson:** Resume-before-start is non-negotiable. `pi-epic-next-feature` checks `in_progress` FIRST and returns the lowest-numbered in-progress fid; only if none is in-progress does it look at the ready set. (Implemented 2026-05-13 in `pi-epic-next-feature`.)

### L-011: copy-paste local extension installs need the full deps tree, not just top-level packages
- **Added:** 2026-05-13 (epic 0001-minikv, setup hand-off)
- **Pattern:** When bootstrapping a new test repo, it's tempting to `cp -r .pi/npm/node_modules/pi-subagents /target/.pi/npm/node_modules/` plus a hand-written `.pi/settings.json`. This silently fails: pi-subagents has 100+ transitive deps that must also be present, AND the settings.json schema requires the key `"packages"` (not `"extensions"`). Symptom: `subagent` tool not found, `pi list` reports "No packages installed."
- **Lesson:** Either (a) `pi install -l npm:pi-subagents npm:pi-intercom` from inside the new repo (which writes the right settings.json AND installs deps), or (b) copy the WHOLE `.pi/npm/` tree (`node_modules/`, `package.json`, `package-lock.json`) plus the `.pi/settings.json` from a known-good repo. Both work; the half-measure does not.

### L-009: orchestrator must inspect, not blindly wait or kill
- **Added:** 2026-05-12 (epic 0001-task-cli, post-mortem)
- **Pattern:** Long-running subagents look the same to a naive parent whether they're (a) deep-thinking, (b) running a slow tool like `npm test`, (c) looping, or (d) hard-stalled. Blind timeouts kill (a)/(b); blind waits hang on (c)/(d).
- **Lesson:** The orchestrator template's `§STALL HANDLING` section requires three steps before kill: (1) call `subagent({action: "status", id})` to read current_tool, current_tool_duration, activity_freshness, recent_output, tokens_in_last_minute; (2) classify into Working / Looping / Stalled / Awaiting-decision / Crashing; (3) NUDGE first via `subagent({action: "resume", id, message})` and only then INTERRUPT. Forensics from `~/.pi/.../async-subagent-runs/<id>/` (events.jsonl + output-N.log) inform the post-interrupt decision: respawn-once vs HALT (H7). Caps: 1 nudge per episode, 1 interrupt-respawn per feature, 20 min total stall budget. Pi already raises automatic needs-attention notices for stalls — the orchestrator just has to react to them with this protocol instead of waiting blindly. (Implemented in `epic-run-auto.md` 2026-05-12.)

### L-012: halt reports must not ride the auto-commit train
- **Added:** 2026-05-13 (epic 0001-minikv, epic-review caught it)
- **Pattern:** When the orchestrator writes `.pi/epics/<id>/halt-<ts>.md` for a recoverable halt and the user resumes, the next `pi-feature-start` runs `git add ".pi/epics/<id>"` to commit straggling design/decomp edits. That glob silently scoops up the halt report, baking it into the epic branch history and eventually into the PR diff. The epic-reviewer caught this (correctly flagged as "Stale halt report committed"), but ideally it never happens.
- **Lesson:** `pi-feature-start` now `git reset HEAD -- ".pi/epics/<id>/halt-*.md"` after staging, so halt reports stay un-tracked operator artifacts. The orchestrator's closeout step does the same `git reset` belt-and-suspenders. (Implemented 2026-05-13 in `pi-feature-start` and `epic-run-auto.md`.)

### L-013: epic meta.yaml status must be advanced explicitly through its lifecycle
- **Added:** 2026-05-13 (epic 0001-minikv, cosmetic but visible in monitoring)
- **Pattern:** `pi-epic-init` sets `status: design`, `pi-epic-complete` sets `status: done`. Nothing in between advances it, so during the entire ~90-min run, monitoring tools and humans grepping `meta.yaml` saw `status: design` even though 11 features were already merged. Cosmetic but misleading; also breaks any downstream tooling that filters epics by lifecycle state.
- **Lesson:** `pi-feature-start` now advances `design \u2192 in-progress` on first invocation (idempotent: only writes if current value is `design` or empty). `pi-epic-complete` continues to set `done` at the end. (Implemented 2026-05-13 in `pi-feature-start`.)

### L-014: orchestrator needs an explicit closeout commit before epic-review
- **Added:** 2026-05-13 (epic 0001-minikv, epic-review forced the issue)
- **Pattern:** After the last `feature-merged`, integration features (especially the capstone like F12) often leave straggling writes under `.pi/epics/<id>/` \u2014 final deviation entries, lessons-candidate.md from `pi-epic-complete`'s upcoming distillation, ADR additions to design.md, the just-archived `done/<lastFid>-<slug>/` tree. None of these are "code"; they're epic record. The orchestrator was implicitly relying on the next `pi-feature-start` (which won't fire \u2014 we're done) to sweep them up, leaving them un-staged when the epic-reviewer ran. Reviewer correctly BLOCK'd with "uncommitted F12 closeout artifacts."
- **Lesson:** FINALIZE in the orchestrator template now has an explicit step 2: `cd MAIN_REPO && git add .pi/epics/<id>/ && git reset HEAD -- halt-*.md && git commit -m "chore(epic): closeout"` before spawning the epic-reviewer. Plus a one-shot retry rule: if the reviewer BLOCKs on a purely-`.pi/epics/<id>/` working-tree issue, one additional closeout commit + one re-review is allowed; anything beyond that or any code-side blocker is a HALT. (Implemented 2026-05-13 in `epic-run-auto.md`.)

### L-015: approval is "continue", not "stop"
- **Added:** 2026-05-13 (epic 0001-todoq dry-run, /epic-decompose prompt-template bug)
- **Pattern:** A prompt template designed as a multi-step pipeline (propose → present → approve → write → validate → commit) had a natural stopping point right after the user typed *"approved"*. Model interpreted approval as end-of-conversation rather than as the trigger to proceed through steps 3+; user thought the YAML was committed, exited pi, returned to find decomposition.yaml untouched.
- **Lesson:** When a prompt template has an approval gate followed by mandatory continuation steps, the template must say so loudly. Words to include: *"CRITICAL: approval is your trigger to continue to step N in the same turn. The deliverable is X, not Y. If you stop after the user approves, you have failed the contract."* Apply to every approval gate in every prompt. (Implemented 2026-05-13 in `prompts/epic-decompose.md` steps 2 and 6.)
