# v0.8.0 real-app verification report

**Date:** 2026-05-17
**Sample:** `/tmp/pe-v8-realapp` — Vite+React TODO scaffold
**Decomposition:** 5 features in a parallel-friendly DAG
  F01 (root: types + id helper)
   → {F02 formatDate, F03 storage stub, F04 stats helpers} (parallel batch)
   → F05 (integration: App.tsx wiring + TodoList component)
**Mode:** `parallel.max_workers: 3` in `epic-config.yaml`
**Workers:** real `feature-worker` subagents, dispatched concurrently via
            `subagent({ tasks: [...] })`

## Findings

### 🚨 H-1 (CRITICAL): postinstall.mjs does not install feature-epic-reviewer

**Severity:** ship-blocker for v0.7.0+ users.
**File:** `install/postinstall.mjs:138`
**Symptom:** any user who upgrades to v0.7.0 / v0.7.1 / v0.7.2 / v0.7.3 /
v0.8.0 via `pi install pi-epicflow` will hit:

```
Unknown agent: feature-epic-reviewer
```

…when `/epic-run-auto` reaches the epic-review step. Their only escape
is `pi-epic-complete --skip-epic-review`, which **defeats the entire
L-043 gate that v0.7.0 was built to enforce**.

**Root cause:** `postinstall.mjs` hardcodes the agent list as
`["feature-worker.md", "feature-reviewer.md", "feature-planner.md"]`
on line 138, and the file-header docstring (line 9) says "the three
helper agents". The list was never updated when v0.7.0 introduced the
fourth agent.

**Why automated smoke missed it:**
- Smoke test runs scripts directly from the repo — it doesn't exercise
  the `pi install pi-epicflow` install path at all.
- The L-043 lesson said "v0.7.0 ships `feature-epic-reviewer`" — true
  for the repo, false for the install.

**Why prior real-app verification missed it:** v0.7.3's real-app run
in `/tmp/pe-sample-todo` used the script-level path (manual `pi-epic-*`
calls) and never invoked `pi-epic-complete` past the L-043 gate.

**Fix (v0.8.1):**
1. Add `"feature-epic-reviewer.md"` to the hardcoded list at line 138.
2. Refactor: derive the list by scanning `agents/*.md` so the next
   added agent doesn't repeat this bug (the install can drift silently
   from what `agents/` ships).
3. Update the docstring count.
4. Add a smoke phase that asserts `~/.pi/agent/agents/` ends up with
   every `.md` in `agents/` after running postinstall against a temp
   `PI_EPICFLOW_AGENTS_DIR`.
5. Add an L-050 lesson: **postinstall + repo-contents drift is a
   recurring failure shape** — derive install lists from repo contents,
   never from a hardcoded list maintained in parallel.

### S-1 (SOFT): Workers reach for `npm install` when build deps aren't pre-staged

**Severity:** recurring deviation pattern; argues for a doc/convention fix,
not a code change.
**Observed:** F01 worker created `package-lock.json` to make `tsc`
available; F05 worker created `src/react-shim.d.ts` because
`tsconfig.json` had `jsx: react-jsx` but no `@types/react`.

Both deviations were **honestly self-reported** in worker-report.md
(the v0.6 audit principle worked), but they also illustrate that
"build passes" ACs implicitly require some toolchain state the
decomposition doesn't always own.

**Under v0.8 parallel mode this is a real bug risk:** if F02, F03, F04
had each independently run `npm install`, they'd all touch
`package-lock.json`. L-049's pre-check wouldn't fire (none declared it),
but `pi-feature-complete` H6 would have fired on the second and third
merges with "Out-of-scope conflicts (worker-discipline)". This run
only avoided it because the orchestrator (me) pre-staged the install
between F01's merge and the parallel batch dispatch.

**Recommended action:**
- Add a section to `agents/feature-worker.md` clarifying: if your AC
  says "build passes" and your worktree lacks an installed toolchain,
  contact_supervisor — don't unilaterally install.
- Add a lesson on the orchestrator side: pre-stage installed deps at
  the epic root after F01-equivalent merges, before any parallel batch.
- Optionally: extend `required_toolchain` validate_cmd to also assert
  "deps installed" (e.g. check `node_modules/.bin/tsc` exists).

### S-2 (SOFT): pi-epic-complete fails non-gracefully when there is no `origin` remote

**Severity:** minor; affects sample/scratch repos and offline development.
**Symptom:** at the very end of `pi-epic-complete`, after the epic has
already been archived locally and lessons distilled, the push step
errors with `fatal: 'origin' does not appear to be a git repository`.
The epic stays in `state: in-progress` even though all the local
finalization work succeeded.

**Recommended action:** wrap the `git push` call in pi-epic-complete
with a "no remote configured" guard that warns + skips rather than
errors. Sample repos and self-hosted/offline flows shouldn't be
penalized.

### S-3 (SOFT): No per-feature reviewer artifacts in this run

**Severity:** verification-run-specific; not a v0.8 bug.
**Observed:** feature-epic-reviewer correctly flagged that no
review-report.md artifacts existed for F01-F05. This is expected for
the verification run — I deliberately skipped per-feature
`feature-reviewer` calls to keep token budget reasonable. For a
production /epic-run-auto run the per-feature reviewer would be
invoked between worker and pi-feature-complete.

The good signal: the **epic reviewer noticed and called it out**,
exactly as the L-043 design intended. Defense in depth working.

## What this verification proved

**Works end-to-end:**
- `epic-config.yaml parallel.max_workers > 1` opt-in
- `pi-epic-next-feature --batch N` ready-set computation with DAG
  topology + L-049 conflict pre-check
- `subagent({ tasks: [...] })` as the orchestrator's P1 dispatch
  primitive — workers really do run concurrently
- In-process FIFO merge queue (P3) — `pi-feature-complete` serializes
  the parallel branch into one linear squash sequence
- v0.7 gates unchanged: feature-epic-reviewer (L-043),
  integration-shell validator on F05 (L-045), per-feature reviewer
  contract honored
- L-048 (in-process queue beats IPC) — orchestration coordination
  lived entirely in shell loop variables; no `flock`, no `.locks/`
  directory, no race condition

**Did not exercise:**
- A real H6 from a worker going out-of-scope into a sibling's territory
  (smoke covers this with a forced collision; this run avoided it
  because the deps were pre-staged).
- A worker-halt during a parallel batch (H1 from one of 3 workers
  while the other 2 keep running).
- `max_workers > 3` (no evidence yet about optimal value).

**Discovered issues for v0.8.1:**
1. **CRITICAL** — `feature-epic-reviewer` not installed by
   `postinstall.mjs` (affects all v0.7.0+ installs).
2. Workers unilaterally `npm install` when build deps aren't staged;
   risks H6 under parallel mode.
3. `pi-epic-complete` push step is fragile when there's no remote.

---

## Decision

**Ship v0.8.1 hotfix** addressing finding 1 (must) and finding 3 (low
effort, high value). Finding 2 gets a worker.md doc clarification +
a new lesson L-050 (postinstall+repo drift) + L-051 (worker should
contact_supervisor before npm install, not just self-report).

Then v0.8.0 + v0.8.1 are the new operator-ready release pair.
