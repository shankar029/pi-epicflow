## TL;DR

Two big shippables and one quality cluster:

1. **Global project-memory overlay** at `~/.pi/global-memory/` —
   personal conventions and decisions that apply across all your repos.
2. **npm distribution** — `pi install npm:pi-epicflow@^0.14` instead
   of the git source. `pi update` now keeps you current automatically.
3. **In-site Quickstart + 9 pages of reference docs** + onboarding
   hardening (proactive EACCES detection, scope-detection fixes, auto-
   cleanup of stale skill tarballs).

**No breaking changes.** v0.13 per-repo behavior is unchanged. The
overlay is opt-in.

## Install / upgrade

```bash
# Fresh install (recommended):
pi install npm:pi-epicflow@^0.14

# Upgrade from v0.13.x or earlier v0.14.x:
pi update pi-epicflow

# Verify:
pi-epicflow-doctor
```

If you hit `EACCES` on Linux/WSL/macOS, see the npm-prefix gotcha in
the [Quickstart](https://shankar029.github.io/pi-epicflow/#/quickstart)
(step 2).

## v0.14.0 — cross-repo project memory

**The pain.** v0.13 shipped per-repo project memory at `.pi/project/`.
After ~2 months of dogfooding across 3–5 active repos, the biggest
recurring friction was re-typing the same personal conventions in each
new repo: "always use ruff over black", "prefer pathlib over os.path",
"JSONL not SQLite for append logs". These aren't project-specific —
they're personal preferences that should follow the operator across
all their work.

**The fix.** v0.14 layers a global overlay underneath the per-repo
brain:

```
~/.pi/global-memory/
├── index.md              # router (autoloaded)
├── global-charter.md     # one paragraph about how you work
├── global-conventions.md # always/never rules across all repos (GC-NNN)
└── global-decisions.md   # stack-level choices across all repos (GD-NNN)
```

Loaded on top of per-repo state. **Per-repo always wins on conflict**
— if your global says "always use ruff" but the project's
`conventions.md` says "this repo uses black", black wins in that repo.

One slash command bootstraps the overlay once per machine:

```
> /project-init-global
```

Then in normal sessions, when you say "always do X", the new
`epicflow-steward` persona decides whether it belongs in the per-repo
`conventions.md` (project-specific) or the global overlay (you'd want
this in every repo). Asks if ambiguous.

### What's new in detail

- **`~/.pi/global-memory/`** layout with 4 files and the `GC-NNN` /
  `GD-NNN` ID prefixes.
- **`/project-init-global`** slash command — one-time per-machine
  bootstrap.
- **`epicflow-steward`** sub-agent — mediates global ↔ per-repo write
  boundary, logs cross-references via `supersedes:`.
- **`epicflow-*` personas all auto-prime** on `~/.pi/global-memory/` in
  addition to `.pi/project/`. Workers and reviewers see the full
  layered context.
- **`pi-epicflow-doctor`** reports overlay status alongside per-repo
  status.

### What stayed the same

- v0.13 per-repo `.pi/project/` works identically.
- Repos without `/project-init-global` having been run see zero
  behavior change.
- All v0.13 design principles still hold: trigger-moment writes,
  work-noun co-occurrence, append-only + supersedes, goal as guardrail,
  C-001 anti-stub.

## v0.14.2 — install hardening (4 smoke-test fixes)

A real install smoke test on a fresh prefix caught 4 issues. All four
are pure surface improvements — no behavioral change for users who
weren't already in a broken state.

1. **postinstall scope detection (L-055).** `pi install npm:pi-epicflow`
   installed under a plain npm-global prefix
   (`/usr/local/lib/node_modules/`, `~/.npm-global/lib/node_modules/`,
   nvm/fnm/Homebrew/volta, `%AppData%\npm\node_modules\`) is now
   correctly recognized as `global` scope. Previously printed
   `WARN: could not detect install scope` and silently skipped the
   auto-install of `pi-subagents` + `pi-intercom`, causing
   mid-`/epic-run-auto` "subagent tool not found" failures.

2. **Stale skill-tarball sweep (L-056).** postinstall now removes any
   leftover `~/.pi/agent/skills/epic-feature-workflow*.tar.gz` from
   pre-v0.4 installs (when pi packaged the skill as a tarball instead
   of an unpacked directory). Pi's own `pi update` never touches
   these, so they accumulated silently.

3. **doctor: proactive npm-prefix EACCES detection (L-054).** New
   `── npm prefix ──` section runs `npm config get prefix`, checks
   writability of `<prefix>/lib/node_modules`, and prints the fix
   recipe inline. Catches THE most common Linux/WSL/macOS onboarding
   cliff (root-owned `/usr/local`) BEFORE the user hits it on the next
   `pi update`. PowerShell parity in `scripts-win/pi-epicflow-doctor.ps1`.

4. **doctor: pending agent-update visibility (L-057).** New
   `── pending agent updates ──` section lists every `*.new` file
   under `~/.pi/agent/agents/` (staged by postinstall's
   non-destructive overwrite) with a one-line `diff` + accept/reject
   recipe. Previously only mentioned in install scrollback.

## Migrations

**None required.** v0.14 is fully backwards-compatible with v0.13.

If you want to opt into the new surfaces:

- **Global overlay:** run `/project-init-global` once per machine.
  Five-minute interactive prompt.
- **Switch from git to npm install:** `pi update pi-epicflow` then
  `pi install npm:pi-epicflow@^0.14`. The settings.json source line
  updates to the npm reference.

## Doctor changes (you'll see new sections)

`pi-epicflow-doctor` now prints two additional sections at the end:

```
── npm prefix ──
  ⚠ npm prefix is NOT writable by <user>: /usr/local
    → 'pi install npm:...' and 'pi update' will fail with EACCES.
    Fix (one-time): point npm at a user-owned prefix:
      mkdir -p ~/.npm-global
      npm config set prefix '~/.npm-global'
      echo 'export PATH=~/.npm-global/bin:$PATH' >> ~/.bashrc
      source ~/.bashrc
    See https://shankar029.github.io/pi-epicflow/#/quickstart for alternatives.

── pending agent updates ──
  ✓ no pending .new files
```

The first only warns if your npm prefix is actually root-owned. If
yours is already user-owned (nvm/fnm/Homebrew/volta), you'll see a
pass.
