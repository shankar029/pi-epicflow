This is sufficient to trigger the validator's SDK-name detection (file path contains "stripe" and content contains "stripe").

## Planted bug

**Shape:** `computeTotal()` in `src/cart.ts` multiplied the sum by `0.9` (a silent 10% "loyalty discount" not reflected in displayed product prices).

```typescript
// BUG: applies hidden discount not visible to user
export function computeTotal(items: LineItem[]): number {
  return Math.round(items.reduce((sum, item) => sum + item.price * item.quantity, 0) * 0.9);
}
```

**Why unit tests miss it:** Unit tests are property-based ("returns positive number", "returns 0 for empty cart"). They don't encode the business invariant that `displayed_price × quantity = cart_total`.

**Why E2E catches it:** The E2E test renders the full app, clicks "Add to Cart" on a $29.99 product, and asserts `cart-total` displays `"Total: $29.99"`. With the bug, it displays `"Total: $26.99"` → assertion fails.

## Substitutions

| Planned | Actual | Reason |
|---------|--------|--------|
| Playwright browser E2E | vitest + @testing-library/react (jsdom) | Avoids `npx playwright install` which requires downloading browser binaries (~200MB) and potentially sudo for system deps. The testing-library approach exercises the same user-flow assertions (click, see, navigate) against the real React component tree. The E2E gate's shell-out mechanism (`run_cmd`) works identically regardless of test runner. |
| 3-feature decomposition | 2-feature decomposition | Sufficient to prove both trigger rules (user-facing verbs + SDK imports). A 3rd feature adds no new signal for the deliverables contract verification. |
| Real Stripe SDK | Hand-rolled `src/lib/stripe.ts` | Per task instructions. Avoids network dependency. Still triggers SDK detection (file named "stripe", content contains "stripe"). |

## Lessons confirmed

### L-056 — Decomposition is the contract for everything the epic ships

**Status:** CONFIRMED (was candidate)

**Evidence:** The validator's trigger→deliverable engine enforces at decomposition time that deliverable surfaces are declared. Specific observations:

1. When F02 had `mock_fixtures` removed, the validator immediately flagged: `scope_file 'src/lib/stripe.ts' references SDK 'stripe', but mock_fixtures is empty`. The error includes a concrete fix suggestion.
2. When F01 had `src/App.tsx` in scope_files (which imports stripe), the content-based detection fired — proving the validator reads actual file content, not just path names.
3. With `strict_deliverables: true`, these are hard errors (exit 1). With `false`, they're warnings only. The progressive rollout path works.
4. **Key signal:** The validator caught a scope assignment mistake (App.tsx in F01 vs F02) that would have caused confusion at implementation time. Decomposition-as-contract surfaces these issues BEFORE workers start.

### L-057 — Mocks owned by the importing feature

**Status:** CONFIRMED (was candidate)

**Evidence:** F02-stripe-checkout declared `mock_fixtures: [tests/e2e/_fixtures/stripe.ts]` and wrote both the calling code (`src/lib/stripe.ts`) and the mock (`tests/e2e/_fixtures/stripe.ts`) in the same feature scope.

1. The mock's response shape (`{ id, amount, currency, status }`) exactly matches the production `PaymentIntent` interface because the same "worker" (me) had just written both.
2. If a different feature had been responsible for the mock, it would have needed to reverse-engineer the call shapes from F02's code — the exact failure mode the design doc predicted.
3. The validator enforces this assignment: if `scope_files` references stripe, `mock_fixtures` must be non-empty IN THAT FEATURE. You can't punt mock authorship to a later feature without an explicit `e2e_skip_reason`.

### L-058 (NEW candidate) — Content-based SDK detection catches transitive imports

**Observation:** The validator's "Layer 2" content-based detection (reading first 100 lines of scope_files for SDK name strings) catches cases where a file doesn't have the SDK in its path but imports it. This caught the App.tsx → stripe import chain that path-based detection alone would miss.

**Impact:** Decomposers should keep the "primary SDK consumer" file in the feature that owns mock_fixtures. Shared files that transitively import SDKs should be scoped to the feature with the mock, not a leaf feature that only uses the non-SDK parts.
